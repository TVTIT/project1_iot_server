# Stage 8.2a — Managed media metadata schema

Migration 28 adds durable intent/verification/cleanup metadata to the existing
`media_objects` table. Existing legacy rows present before migration remain
`managed=false`;
their `storage_path`, declared `media_type`, sizes, checksum, and validation
status are not rewritten or interpreted as proof of upload or verification.
An unmanaged row remains outside the managed lifecycle and its historical
`checksum` is never copied into `verified_sha256`.

## Column contract for the next implementation slice

- `managed`, `upload_id`, and `gateway_id` identify a backend-managed upload.
  `upload_id` is bounded text matching
  `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$` and is the protocol's stable idempotency
  key scoped to a Gateway; it need not be a UUID. `media_id` remains UUID and is
  server generated. Uniqueness applies only to managed rows.
- Managed media is the fixed `video/mp4` type. In the separate private video
  bucket, `storage_path` is exactly `<media_id UUID>.mp4`, generated by the
  server, never from the client ID. The managed-only unique path index and
  check enforce this convention; legacy image paths are unaffected.
- `captured_at` is the Gateway-reported capture time. `created_at` remains the
  server intent creation time. `intent_expires_at` bounds the upload intent;
  `latest_upload_grant_expires_at` stores the conservative maximum expiry of
  any grant reserved before signing (and later issued) for the intent, not a URL
  or token. A failed signer still leaves that conservative value in place;
  subsequent grant reservation advances it with `GREATEST(old, new_horizon)`.
- Migration 28's `upload_grant_generation` fences stale post-sign checks. The
  repository reserves a conservative horizon and sets `next_reconcile_at`
  before Storage signing begins. It covers the bounded signing request timeout,
  the configured signed URL TTL, and the in-flight grace. It stores no URL or
  token. An unresolved reservation remains a grant fence if signing or its
  confirmation fails; only a generation-matched confirmed-missing verification
  transition clears `next_reconcile_at`. Cleanup still waits for
  `latest_upload_grant_expires_at`.
- Existing `media_type` is the declared type and `expected_size` the declared
  byte count (1–80,000,000). `declared_sha256` is the client-declared lowercase
  SHA-256 hex digest. `actual_size`, `actual_media_type`, and `verified_sha256`
  are independently measured by the validator. Existing `checksum` remains
  legacy-only; it is not verification evidence.
- Managed `validation_status` values are exactly `pending`, `verifying`,
  `ready`, `rejected`, and `expired`. `pending` is a committed intent;
  `verifying` means a completion/reconciliation request is durably recorded.
  A `ready`
  row must have matching declared/verified SHA-256, exact declared/actual size,
  and matching measured/declared MIME type. The API/repository must only make a row ready after
  content validation; the database does not inspect Storage bytes.
- `verification_attempts`, `next_verification_at`, `last_verification_at`, and
  `last_verification_error` make retries restart-safe. `next_reconcile_at` is
  the durable due time for Storage/metadata reconciliation. Each new verifier
  claim increments `verification_generation`; a worker carries that generation
  and may commit completion only when it still matches, fencing stale worker
  results without storing a claim token.
- `terminal_reason` is required for `rejected` and `expired`. Cleanup is
  orthogonal: `cleanup_scheduled_at` is a durable no-earlier-than cleanup time,
  constrained to be at or after both the intent deadline and the conservative
  latest grant expiry. `cleanup_attempts` and `cleanup_confirmed_at` persist
  cleanup progress/confirmation. Cleanup must not change `validation_status` or
  `terminal_reason`; replay/lookup therefore returns the original terminal
  result even after object removal.
- Candidate workers should claim due rows in bounded batches using the due-time
  indexes and short transactions. Quota admission can serialize with a global
  transaction advisory lock; no counter table is introduced here. The current
  migration does not implement admission, Storage operations, tokens/URLs,
  verification workers, or runtime feature enablement.

The existing `media_objects_select_policy` continues to gate user reads through
`user_gateways`; existing backend table grants remain in place and direct
anonymous/authenticated writes are explicitly denied. This schema change does
not change media-off behavior or imply Stage 8 completion.

The Stage 6 retention SQL continues to require the exact migration-27 name and
supports only terminal schema 27 or the known additive successor
`28:stage8_media_metadata`; unknown or misnamed future terminals remain refused.
